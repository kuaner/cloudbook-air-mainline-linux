# CloudBook Air 4.19 与 6.12 内核差异及外设映射分析

> **依据规程**：`rk-linux-bringup-skill`（当时使用的本地规程）
> **证据级别**：L1 物理量（万用表/指示灯/屏幕画面）> L2 运行时（sysfs/dmesg/串口）> L3 固件与源码（反编译DTB/配置/内核源码）  
> **硬件平台**：ZTE / China Mobile CloudBook Air 14" (CT2000-24RTW, RK3568B2, 主板型号 W620D V12.0)  
> **基线事实源**：原厂 4.19.193 验证基线（`boot_linux_factory_419_uart.img`）  
> **比对目标**：主线 Linux 6.12.117 LTS 移植候选（`mainline-6.12/`）

> **结论状态（2026-11-12 晚修订）**：本报告中“CPU DVFS 欠压触发 PMIC Latch”的因果链是 v4 阶段的推断，已被 v7 实测推翻：v7 去掉 `cpu-supply` 后仍在约 4.2 秒复位。原文保留作为分析过程，但不再作为已证实根因。v8 已成为首个进入 Armbian 用户态的镜像；4.2 秒复位的完整机制仍需后续对照实验确认。

## 1. 背景与对账目标

在先前的适配工作中，已建立起一个经实机全面验证闭环的 **4.19 Linux 黄金基线**（原厂 4.19.193 内核 + `factory_w620d_v12.dtb` + 自定义最小 initramfs + USB Armbian Trixie Rootfs）：
- 内置 eDP 屏幕（BOE NV140WUM-N44 `1920×1200@60Hz`）由 Xorg modesetting 稳定点亮；
- 内置键盘（SINO WEALTH USB HID）、触控板（I2C-HID `touchpad@2c`）、RK809 音频（扬声器播放）、HDMI 镜像输出、USB 摄像头（MJPEG 视频采集）及 `rtcwake -m mem` 睡眠唤醒均已验证可用。

然而，在推进主线 **Linux 6.12.117** 最小启动阶段（P3 G3 阶段）时，经历了四版迭代（v1~v4），均未成功进入控制台；v4 还出现整机断电，当时怀疑为 PMIC 欠压锁死，但该因果后被 v7 推翻：
- **v1**：停在 SDIO Wi-Fi 阻塞（`dwmmc_rockchip fe2c0000.mmc: card is non-removable`）；
- **v2**：禁用 SDIO 后，越过 mmc1，但停在启动约 4.2 秒处的 `clk: Disabling unused clocks` / `PM: genpd: Disabling unused power domains`；
- **v3**：引入 `clk_ignore_unused pd_ignore_unused initcall_debug` 诊断，日志显示在 `devfreq_init` 返回 0 后停滞；
- **v4**：跳过 `devfreq_event_init` 并关闭 `cpuidle` 后，系统在 `calling devfreq_init` 瞬间断电锁死，电源键与充电指示灯无响应（经长按 15~20 秒硬件复位才恢复 Android 11）。

本报告遵照 `rk-linux-bringup-skill` 的规范，通过 **语义级设备树对账（`dtb_semdiff.py`）**、**内核配置对比（`diffconfig`）** 与 **反编译固件/运行时日志**，系统性解剖 4.19 原厂内核与 6.12 主线内核在底层电源、时钟域、总线拓扑及驱动架构上的根本代差，记录当时的故障假设与后续验证结果，并给出符合 P3 G3 规范的极简安全点亮方案。

## 3. 设备树语义级全景对账 (DTB Semantic Diff)

使用 `dtb_semdiff.py` 比对 `factory_w620d_v12.dtb` (A) 与 `mainline-6.12/rk3568-ecloudbook-air-24rtw.dtb` (B)。

### 3.1 供电拓扑与 CPU DVFS 对账（v4 阶段假设，已被 v7 推翻）

#### 厂端 4.19 事实（A 侧）
1. 在 I2C0 总线（`0xfdd40000`）上声明了 3 个兼容的 CPU 稳压器节点：
   - `tcs4525@1c`：`regulator-name = "vdd_cpu"`（真机 `0-001c: Failed to get chip ID!`，未贴片）；
   - `rk860-0@40`：`compatible = "silergy,syr827"`，`regulator-name = "vdd_cpu"`（**实机 Option[8] Rev[1]，已贴片且工作**）；
   - `rk860-1@41`：`regulator-name = "vdd_cpu"`（真机 `0-0041: Failed to get chip ID!`，未贴片）。
2. 在 CPU 节点 `/cpus/cpu@0` 中：
   - **根本没有声明 `cpu-supply`**，仅包含 `regulator-name = "vdd_cpu";` 字符串。
   - 原厂内核专有的 `rockchip-cpufreq` 驱动通过稳压器名称 `"vdd_cpu"` 进行匹配，哪个芯片 Probe 成功就绑定哪个。
3. U-Boot 与内核启动阶段均将 `rk860-0@40` 稳定钳位在 **1000000 uV (1.00V)**。

#### 6.12 主线当前实现（B 侧）
1. 在 I2C0 上声明了 `vdd_cpu: regulator@40`，兼容 `"silergy,syr827"`，指定 `regulator-min-microvolt = <712500>`，`regulator-max-microvolt = <1390000>`。
2. 在 CPU 节点中显式挂接：`cpu-supply = <&vdd_cpu>;`。
3. 主线 `rk356x-base.dtsi` 附带的 `cpu0_opp_table` 包含了从 408 MHz（**900000 uV = 0.90V**）到 1.99 GHz（1.15V）的多档调频调压点。

#### v4 阶段的工作假设：DVFS 调压可能触发 PMIC 保护（未证实）

以下是当时基于 v4 断电现象提出的假设，不是已证明结论：

1. **调压步进与斜率不匹配**：SYR827 芯片在没有瑞芯微专有寄存器校准逻辑的情况下，当 `cpufreq-dt` 或 `devfreq` 尝试动态调压时，下调电压触发了过冲或瞬间欠压；
2. **硬件级联保护机制（当时推测）**：笔记本电池供电管理由南芯 SC2021 + TI BQ25700 控制，RK817/RK809 PMIC 监控主供电轨。当时认为一旦 CPU 核心电压瞬间跌破阈值，PMIC 内部的硬件保护寄存器可能触发锁死（PMIC Latch-off），关闭 LDO 与 DC-DC，导致外接设备断电、指示灯熄灭、笔记本完全失去响应；该机制未获得直接测量证实。

> **反证（v7/v8）**：v7 已移除 CPU `cpu-supply` 绑定，系统仍在约 4.2 秒复位；因此该假设不能单独解释全部复位。v8 早期读到 DW watchdog `cr=0x00000008`（使能位 0），也不能把 U-Boot 遗留 watchdog 当作唯一根因。

## 4. 6.12 启动停滞与 v4 断电现象复盘（含已推翻假设）

基于真机 4 次试验的串口与系统日志，梳理出 6.12 启动停止的逐级推进链条：

### 4.1 第一停滞点（v1）：SDIO Wi-Fi (`mmc1`) 死锁
- **现象**：停在 `dwmmc_rockchip fe2c0000.mmc: allocated mmc-pwrseq` -> `mmc_host mmc1: card is non-removable.`；
- **根因**：本机的 MT7663S 处于固定 1.8V 供电轨，缺少 `zte,sdio-fixed-1-8v` 补丁时，主线驱动尝试发送 `CMD11` 执行电压协商，SDIO 控制器无应答导致内核卡在探测循环中；
- **解决验证**：v2 将 `&sdmmc1` 标记为 `disabled` 后，日志顺利越过此处，**证明 SDIO 确实是 v1 的首要阻塞点**。

### 4.2 第二停滞点（v2）：激进的 Unused Clocks / GenPD 切断
- **现象**：越过 mmc1 后，在 `4.198s` 打印 `clk: Disabling unused clocks` -> `PM: genpd: Disabling unused power domains` -> `ALSA device list:` 后静默；
- **当时推断的机制（未完全证实）**：
  1. 在 6.12 DTS 中，开启了 33 个硬件节点（包括 VOP2、HDMI、GPU、I2S、PDM、SARADC 等）；
  2. 但内核配置中，DRM、Sound、GPU、I2C-HID 全部被编译成了**可加载模块 (`=m`)**，在首启最小 initramfs 阶段根本没有对应驱动去 claim 这些设备；
  3. 当内核初始化走到 `late_initcall_sync(clk_disable_unused)` 和 `genpd_power_off_unused` 时，内核认为这些时钟和电源域“无人使用”，强行关闭了 `pd_vo`、`pd_gpu`、`pd_vi` 及相关总线 AXI/AHB 时钟；
  4. 此时硬件控制器仍处于上电初态，突然断时钟/断电导致内部 AXI 总线产生未决事务悬挂（AXI Bus Hang），系统在数毫秒内彻底锁死。

### 4.3 第三停滞点与 v4 断电（v3 & v4）：DVFS 欠压是当时假设，非已证实根因
- **现象**：
  - v3 加入 `clk_ignore_unused pd_ignore_unused initcall_debug` 后，越过了电源域关闭阶段，但卡在 `devfreq_init` 返回 0 与后续 initcall 之间；
  - v4 尝试跳过 `devfreq_event_init` 并关闭 `cpuidle` 后，系统在 `calling devfreq_init` 瞬间断电锁死，触发 PMIC 保护（需长按电源键 20 秒物理复位）；
- **当时的工作假设（已被 v7 推翻）**：
  1. 6.12 启用了 `CONFIG_PM_DEVFREQ=y`，并在 DTS 中保留了 `gpu_opp_table` 与 `cpu0_opp_table`；
  2. DTS 中配置了 `cpu-supply = <&vdd_cpu>`，指向 SYR827 芯片（`regulator@40`），但缺少厂商专有的电压偏置校准与延迟补偿；
  3. 当内核初始化到 `devfreq` / `cpufreq` 框架时，驱动尝试探查或微调 CPU / GPU 工作电压；
  4. 当时怀疑 SYR827 供电轨骤降，瞬时电压低于 RK3568 核心运行下限，触发 PMIC（RK817/RK809）与整机电池管理芯片（SC2021）的欠压死锁保护（Undervoltage Lockout / PMIC Latch）；
  5. 整个供电链路切断进入保护模式，在外部表现为机器“瞬间关机且变砖”。

> **反证**：v7 去掉 CPU `cpu-supply` 后仍在约 4.2 秒复位，说明“DVFS 调压欠压”不是充分原因。v4 的断电现象仍需结合 U-Boot 交接、PMIC/EC 状态和启动时序继续定位；在获得直接证据前，不应再把 PMIC Latch 写成已证实根因。

## 5. 符合 rk-linux-bringup-skill 的 G3 极简点亮方案

`rk-linux-bringup-skill` 在 **04 引导与点亮** 第 5 节明确规定了首版点亮的铁律：

> **首版 dtb 的最小集**：只开调试串口、电源（固定电压）、存储（eMMC/SD）、网口、USB。  
> **其他全部 disabled**。失败面越小越好；每加一类都要能解释“为什么现在加”。

### 5.1 设备树手术级精简原则（五关五留）

1. **彻底拔除 CPU/GPU DVFS 动态调频**：
   - 移除 `&cpu0`..`&cpu3` 的 `cpu-supply = <&vdd_cpu>;` 属性（或仅保留固定 1.0V 不调压）；
   - 彻底禁用 `&gpu`（`status = "disabled"`），绝不在 P3 阶段触碰 GPU devfreq；
   - 确保 `vdd_cpu` 稳压器电压锁定为固定值（`1000000 uV`），`regulator-always-on`，禁止任何框架尝试修改电压。
2. **建议禁用硬件看门狗 (`&wdt`)，但 v5/v8 实际未落实**：
   - 设计意图是将 `&wdt` 设为 `status = "disabled"`，避免内核初始化过程因超时触发硬件复位；
   - **事实核对**：`rk3568-ecloudbook-air-24rtw-v5-g3-clean.dts`、当前 6.12 DTS 与 v8 DTB 中 `&wdt` 仍为 `status = "okay"`。后续若要禁用，必须改 DTS 并重建 DTB，不能沿用“已禁用”的旧描述。
3. **禁用所有未加载驱动的多媒体与非必要节点**：
   - 禁用 `&vop`、`&vop_mmu`、`&hdmi`、`&edp`（首版点亮以 UART 登录为唯一判据，显示留到 P4 再开）；
   - 禁用 `&i2s0_8ch`、`&i2s1_8ch`、`&pdm`、`&rk809_sound`（音频留到 P4）；
   - 禁用 `&sdmmc1`（Wi-Fi 留到 P4 配合补丁开启）；
   - 禁用 `&saradc`、`&tsadc` 等非核心控制器。
4. **保留且仅保留 G3 核心节点**：
   - 调试串口：`&uart2 { status = "okay"; }`，`chosen { stdout-path = "serial2:115200n8"; }`；
   - 核心电源：`&i2c0` 上的 `pmic@20`（RK809）与固定电压轨；
   - 存储系统：内置 eMMC `&sdhci`（`mmc@fe310000`）；
   - USB 控制器：`&usb_host0_xhci`、`&usb_host1_xhci`、`&usb_host0_ehci`（用于挂载 U 盘 Rootfs）；
   - 基础 USB 5V 供电与 Hub 复位 GPIO。

### 5.2 启动参数（cmdline）防御性配置

首启候选镜像使用如下防御性参数，彻底消除时钟与电源域的关闭风险：

```text
console=ttyS2,115200n8 earlycon=uart8250,mmio32,0xfe660000 root=LABEL=ROOTFS rootfstype=ext4 rootwait rw clk_ignore_unused pd_ignore_unused cpuidle.off=1 initcall_debug
```

- `clk_ignore_unused` & `pd_ignore_unused`：防止 late-init 误关未知依赖时钟；
- `cpuidle.off=1`：禁用 CPU 低功耗休眠，消除时钟门控时序竞争；
- `initcall_debug`：保留单步跟踪，精确记录每一个驱动的耗时与返回码。

## 6. 结论与对账矩阵总结

| 关键域 | 4.19 原厂基线事实 (已验证) | 6.12 现状 (问题点) | G3 最终整改对策 |
| :--- | :--- | :--- | :--- |
| **CPU 供电** | `rk860-0@40` (Option 8 Rev 1)，固定 1.0V，无 `cpu-supply` 绑定 | 开启 `cpu-supply` + OPP 调压；v4 断电曾怀疑欠压，但 v7 去除此绑定后仍复位，因果未证实 | **保持固定 1.0V；是否保留 `cpu-supply` 需对照实验确认** |
| **显示子系统** | 内置 DRM (`=y`)，无 VT，Xorg modesetting 点亮 | DRM 为模块 (`=m`)，DTS 提前开启 VOP2，存在时钟/电源域风险 | **首版点亮完全禁用 VOP2/HDMI/eDP** |
| **时钟电源域** | 厂商时钟树默认常开 | v2 在 late-init 关闭未 claim 时钟/电源域时停滞；`clk/pd ignore` 后可越过，但机制未完全证实 | **保留 `clk_ignore_unused pd_ignore_unused`** |
| **SDIO Wi-Fi** | 厂商专有 1.8V 补丁与驱动 | 主线标准协商 `CMD11` 超时死锁 | **保持 `status = "disabled"`，P4 再处理** |
| **输入与音频** | 内置驱动，实机正常工作 | 驱动全为模块 (`=m`)，DTS 开启致无用消耗 | **首版禁用音频节点，留待模块就位后开启** |
| **硬件看门狗** | 运行时未超时 | 4.19/6.12 DTS 均为 `okay`；v8 早期 `cr=0x8`（未使能），probe 后注册 `timeout=44`；不能证明是 4.2 秒复位根因 | **P4 前做对照实验；若决定禁用，改 DTS 后重建 DTB** |

通过以上对账，我们给出了 6.12 v1~v4 启动失败的**工作假设**和 G3 收敛方向；v7/v8 已证明“DVFS 欠压”解释不完整。v8 实测进入 Armbian 用户态，说明 G3 极简集足以完成首启；4.2 秒复位的完整根因仍待后续对照实验确认。
